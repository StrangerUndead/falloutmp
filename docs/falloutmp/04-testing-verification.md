# 04 — Testing & Verification Strategy

Principle (ADR-015): everything that can be verified on Linux is verified on Linux by Claude. Windows-only code is compile-verified in CI. In-game behaviour is verified by the user through a **self-test plugin** (automatic, JSON report) or **written manual scripts**. Every task names its verification mode (README §4).

## 1. Test pyramid

| Layer | What | Where | Runs | Owner |
|---|---|---|---|---|
| Unit (C++) | libespm, papyrus-vm, serialization, server (`PartOne`-level) | `unit/` Catch2 | Linux container, every change | Claude |
| Fixture | Parsers against synthetic plugins, PEX and BA2 | `unit/` + `unit/fixtures/` | Linux | Claude |
| Unit (TS) | Client sync logic with mocked `falloutPlatform`; gamemode logic | `falloutmp-client/test/`, `falloutmp-gamemode/test/` | Linux (`yarn test`) | Claude |
| Integration | Real server process + scripted bot clients (protocol level) | `misc/tests/` style, `QA-020` bots | Linux | Claude |
| Compile | Platform DLLs, client bundle, Windows unit build | GitHub Actions `windows-2022` | On push | Claude (reads CI) |
| Self-test (in game) | Scripted checks inside Fallout 4 | `falloutmp-selftest.js` + PLAT-091 | User's PC, one launch | User runs, Claude analyses |
| Manual (in game) | Multiplayer scenarios (2+ clients) | `docs/falloutmp/test-scripts/*.md` | User (and friends) | User runs, Claude analyses |
| Real data | Fallout4.esm/DLC parsing and gameplay data checks | `[fo4data]` tag | User's machine or private runner | User runs |
| Load/soak | 100 bots / 2 h sessions | QA-020, QA-030 | Linux / user | Claude / user |

## 2. Linux build & run (Claude)
- Bootstrap: [reference/dev-environment.md](reference/dev-environment.md) §0 and §6 (ENV-001). Expect about 25 min cold.
- Inner loop:
  ```bash
  cd build
  cmake --build . --target unit     # incremental: a one-file change takes 33–44 s
  ./unit/unit "[F04]"
  ```
- Tag conventions:
  - `[Fxx]` for feature tests;
  - `[espm]` for anything that needs Skyrim data (auto-skipped without data);
  - `[fo4data]` for anything that needs Fallout 4 data (auto-skipped without data; new switch in `unit/main.cpp`, ESPM-015);
  - existing upstream tags stay as they are.
- `unit/main.cpp` must detect both data sets independently: `SKYRIM_DATA_DIR` and `FO4_DATA_DIR`.

## 3. Fixtures without Bethesda data
- **Plugins:** `unit/PluginBuilder.h` (ESPM-002) builds TES4/GRUP/records/subrecords in memory, with compression and ESL flags, in either the Skyrim or the FO4 form version. Layouts are taken from reference/fo4-data-formats.md.
- **PEX:** golden FO4 `.pex` compiled from our own `.psc` sources with upstream Caprica in Windows CI (ENV-013). They are committed with their sources. Also write byte-level tests that hand-assemble small PEX images.
- **BA2:** generate small GNRL archives in tests if rsm-bsa can write them; otherwise use a tiny hand-assembled archive.
- **Saves:** synthetic `.fos` headers for the DATA-020 parser tests.
- **Rule:** fixtures are generated by our code or written by us. Never extract them from game files.

## 4. Client logic tests (L-ts, CLI-050)
- A mock `falloutPlatform` module provides fake forms, actors and references with settable state, an event emitter for game events, a controllable clock, and a recorder of native calls.
- Suites:
  - movement interpolation and snap rules;
  - action/event capture filters and sequence ordering;
  - inventory diffing;
  - container flows;
  - message encoding of TS objects to the expected JSON.
- The same harness lets gamemode tests exercise `ctx.sp` snippets.

## 5. In-game verification (with the user)

### 5.1 Self-test plugin (QA-010, PLAT-091)
- Enabled with `FalloutPlatform.ini` → `[Debug] bSelfTest=1`, or by dropping `falloutmp-selftest.js` into `Data/Platform/Plugins`.
- Runs after the first `update`. Each check is a small async function with a timeout. The output is `Documents/My Games/Fallout4/F4SE/falloutmp-selftest-<sha>.json`:
  ```json
  {"sha":"…","runtime":"1.11.x","f4se":"0.7.x","checks":[{"id":"PLAT-030.natives","status":"pass","detail":"912 natives","ms":12}]}
  ```
- **Check catalogue** (grows with features). Each check id matches a task id:
  - init/log line;
  - JS hot reload;
  - update/tick;
  - overlay draw;
  - reflection (static/member/latent calls; struct/Var marshalling);
  - events triggered via console commands;
  - spawn of a remote actor with appearance/equipment;
  - inventory read/write round trip;
  - lock state;
  - weather/time set;
  - animation probes (`dumpGraphVariables`).
- Claude parses the JSON, updates STATUS.md and opens follow-up tasks.

### 5.2 Manual scenarios
- One script per feature milestone in `docs/falloutmp/test-scripts/`, using the request template from [06-workflow-conventions.md §6](06-workflow-conventions.md).
- Each script lists setup, numbered steps, expected results and what to send back: logs, the self-test JSON, short videos for animation.
- Multiplayer scenarios need two clients. Investigate running two instances on one PC (QA-050: single-instance patch, prior-art C18).
- Results go into STATUS.md → Evidence log.

### 5.3 Logs to collect
- `Documents/My Games/Fallout4/F4SE/f4se.log`
- `FalloutPlatform.log`
- `falloutmp-selftest-*.json`
- Crash logs from Buffout 4, if installed
- Server console output
- Prometheus metrics snapshot (if relevant)

## 6. CI matrix (target)
| Job | Runner | Contents |
|---|---|---|
| linux-build | ubuntu (Docker or plain) | server, libs, unit (`~[espm]` without data; Skyrim data job for upstream parity), TS builds, `yarn test` |
| windows-skyrim | windows-2022 | upstream Skyrim build (keeps upstream merges honest) |
| windows-fallout4 | windows-2022 | fallout4-platform, MpClientPlugin, falloutmp-client bundle, artifacts `fallout4-platform-<sha>` |

| lint | ubuntu | linter-config.json checks |

## 7. Non-functional tests
- **Load:** QA-020 runs 100 bots moving, shooting and trading, with 300 hosted NPCs. It records server tick p95, bandwidth per client and the message mix.
- **Network conditions:** QA-021 adds jitter and loss, checks for rubber-banding and measures the hit false-reject rate.
- **Persistence/adversarial:** QA-040 attempts duplication: concurrent take/put, disconnect mid-transfer, crash between mutation and flush, replayed messages.
- **Security:** fuzz the BitStream reader (NET-008). Check every message for ownership and rate limits. The gamemode JS signing stays enforced.
- **Soak:** QA-030 runs 2 h with 10 players.

## 8. Definition of evidence (for STATUS.md)
Each completed task records one or more of these:
- the commit SHA;
- the unit test names/tags that pass;
- the CI run link;
- the self-test check ids with status;
- the manual test script id with tester and date;
- metrics.

A task without evidence stays `[~]`.
